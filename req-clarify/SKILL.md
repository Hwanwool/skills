# 需求澄清（Requirement Clarify）

## ⚠️ 强制性约束（必须遵守，违反即流程失效）

以下规则是**硬性约束**，优先级高于本文件中所有其他指导性描述。任何违反这些约束的行为都意味着本 skill 流程失效，必须立即回退纠正。

### 约束 1：一次只问一个问题

- **每轮对话只提一个问题**。禁止在同一轮回复中抛出多个问题或多个待澄清点。
- 每个问题必须附带 1~3 个你认为合理可行的方案选项供用户选择（除非该问题确实只有二元答案）。
- 如果发现自己正在或计划提出多个问题，必须精简到只保留最核心的一个。

### 约束 2：未澄清完不得进入实现阶段

- **在需求清单未达到"完备"状态前，禁止输出任何实现代码**。
- 本 skill 的目的是"澄清需求"，不是"实现需求"。所有代码输出必须等到需求澄清流程结束后由其他 skill（如 `incremental-dev`）处理。

### 约束 3：终审确认后方可移交

当需求清单达到步骤 5 终审确认后：

- 必须先输出**最终版需求清单**和**整体方案评估**（包含架构影响、涉及的文件、实现路径等）
- 然后**明确等待用户确认**。用户确认的标志是用户主动回复"确认"、"没问题"、"可以执行"、"开始实施"等明确信号。
- 用户确认后，需要用户**明确声称执行方案**（如"开始执行"、"进入开发"、"启动 incremental-dev"等），才能进入编码阶段。
- 不得在用户未明确声称执行方案的情况下自行开始编码。

### 约束 4：多 skill 协同时的执行顺序

当本 skill 与 `incremental-dev` 或其他实现类 skill **同时开启**（例如用户一次消息中同时触发两者）时，执行顺序如下：

```
步骤 A：运行 req-clarify 完成需求澄清 → 输出最终方案
步骤 B：等待用户确认最终方案
步骤 C：等待用户明确声称"开始执行"
步骤 D：只有到步骤 C 之后，才允许进入编码/实现阶段
```

除非用户**明确声明"不需要澄清，直接开始"**，否则不允许跳过上述顺序。

### 约束 5：响应前自我审查

在每次即将输出内容前，必须按以下顺序做自我审查，全部通过才能输出：

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 本轮只提了一个问题（在澄清阶段）？ | 是 → 继续；否 → 删除多余问题，只保留一个 |
| 2 | 问题是否附带了 1~3 个方案选项？ | 是 → 继续；否 → 补充选项（除非是二元问题） |
| 3 | 需求清单是否已达到"完备"？ | 否 → 继续澄清（禁止输出代码）；是 → 进入终审确认 |
| 4 | 用户已确认最终方案并明确声称执行？ | 是 → 可进入编码；否 → 等待用户确认和声称 |

任何一项不通过，都必须**先修正再输出**，不得绕过。

## 触发场景

当用户提出一个新的功能需求、特性请求或修改要求时，自动启用本 skill 进行需求澄清。

## 核心原则

1. **一次只问一个问题** — 每次提问仅聚焦一个未阐明的方面，避免多个问题同时抛出造成混乱
2. **提供选项而非开放问题** — 每次提问给出你认为可能合适的 1~3 条方案选项供用户选择
3. **迭代推进** — 每获得一次回答后，将结果整合进需求清单，基于更新后的清单提出下一个问题
4. **完备即止** — 当需求清单足够清晰、完整、可执行时，停止提问

## 执行流程

### 步骤 1：初始化需求清单

- 解析用户的需求描述，提取已明确的信息，整理成结构化需求清单
- 需求清单应包含：功能描述、交互方式、数据流、UI 表现、边界条件等维度
- 标记出当前清单中模糊、缺失或矛盾的部分

### 步骤 2：阅读相关工程文件

- 搜索并阅读与需求相关的现有代码、配置、预制体、设计文档等
- 了解现有的架构模式、编码规范和实现约束
- 将工程上下文整合进需求理解中，避免提出与现有设计冲突的问题

### 步骤 3：迭代提问

每次迭代：

1. 审视当前需求清单，找出最关键的待澄清点
2. 针对该点提出一个问题
3. 提供 1~3 个你认为合理可行的方案选项供用户选择
4. 等待用户回答

### 步骤 4：整合与更新

- 将用户的回答及选择的方案整合进需求清单
- 更新清单中对应条目的状态为「已确认」
- 如果用户的选择引入了新的模糊点，标记为新待澄清项

### 步骤 5：终审确认

在需求清单已完备、迭代提问终止后：

- 重新审查相关的工程代码、配置文件、预制体等
- 对照需求清单逐项核查，检查是否存在：
  - 与现有架构/实现冲突的条目
  - 遗漏的边界情况或异常流程
  - 前后决策之间的矛盾
  - 缺少必要输入/输出数据的环节
- 若发现纰漏，标记为新的待澄清项，回到步骤 3 继续迭代
- 若确认不存在纰漏，则最终定稿需求清单

### 步骤 6：循环与终止

- 回到步骤 3，基于更新后的清单继续提问
- 终止条件（满足任一即可）：
  - 需求清单中所有关键字段均已确认
  - 剩余未确认项不影响功能实现的主流程
  - 用户明确表示清单已足够完备

## 需求清单模板

使用以下结构化格式维护需求清单：

```markdown
## 需求清单：[功能名称]

### 已确认
- [x] 条目 1（描述+确认的决策）
- [x] 条目 2

### 待澄清
- [ ] 条目 3（当前待解决的问题）
- [ ] 条目 4

### 方案记录
- 条目 3 → 已提供选项 A/B/C，等待用户选择
- 条目 5 → 用户选择了方案 B
```

## 提问示例

**不好的提问方式：**
> "这个功能需要怎么触发？数据从哪里来？UI 怎么展示？有没有边界情况要处理？"

**好的提问方式：**
> **问题：这个功能的触发方式是什么？**
> A. 点击按钮手动触发
> B. 进入场景时自动触发
> C. 通过拖拽物品到目标区域触发

## 注意事项

- 优先澄清影响架构设计和高层决策的问题（如数据流向、模块边界），再处理细节问题（如 UI 布局、颜色）
- 如果某个问题可以从现有工程文件中找到明确答案，不要提问，直接补充进清单
- 每次提问尽量附带工程上下文依据，如 "当前项目中同类功能的实现方式是 X，新功能是否沿用相同模式？"
- 记录所有已确认的决策，避免后续重复提问
