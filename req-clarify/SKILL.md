# 需求澄清（Requirement Clarify）

## ⚠️ 强制性约束（必须遵守，违反即流程失效）

以下规则是**硬性约束**，优先级高于本文件中所有其他指导性描述。任何违反这些约束的行为都意味着本 skill 流程失效，必须立即回退纠正。

### 约束 1：一次只问一个问题

- **每轮对话只提一个问题**。禁止在同一轮回复中抛出多个问题或多个待澄清点。
- 每个问题必须附带 1~3 个你认为合理可行的方案选项供用户选择（除非该问题确实只有二元答案）。
- 如果发现自己正在或计划提出多个问题，必须精简到只保留最核心的一个。
- **禁止使用结构化提问工具**（如 omp 的 `ask` 工具、AskUserQuestion 等弹窗式提问）：所有提问一律以回复正文的**文本**形式呈现，不得调用任何结构化选项弹窗工具。

### 约束 2：未澄清完不得进入实现阶段

- **在需求清单未达到"完备"状态前，禁止输出任何实现代码**。
- 本 skill 的目的是"澄清需求"，不是"实现需求"。所有代码输出必须等到需求澄清流程结束后由其他 skill（如 `incremental-dev`）处理。

### 约束 3：终审确认后方可移交

当需求清单达到步骤 5 终审确认后：

- 必须先输出**最终版需求清单**和**整体方案评估**（包含架构影响、涉及的文件、实现路径等）
- 然后**明确等待用户确认**。用户确认的标志是用户主动回复"确认"、"没问题"、"可以执行"、"开始实施"等明确信号。
- 用户确认后，需要用户**明确声称执行方案**（如"开始执行"、"进入开发"、"启动 incremental-dev"等），才能进入编码阶段。
- 不得在用户未明确声称执行方案的情况下自行开始编码。

### 约束 4：多 skill 协同时的执行顺序

当本 skill 与 `incremental-dev` 或其他实现类 skill **同时开启**（例如用户一次消息中同时触发两者）时，执行顺序如下：

```
步骤 A：运行 req-clarify 完成需求澄清 → 输出最终方案
步骤 B：等待用户确认最终方案
步骤 C：等待用户明确声称"开始执行"
步骤 D：只有到步骤 C 之后，才允许进入编码/实现阶段
```

除非用户**明确声明"不需要澄清，直接开始"**，否则不允许跳过上述顺序。

### 约束 5：响应前自我审查

在每次即将输出内容前，必须按以下顺序做自我审查，全部通过才能输出：

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 本轮只提了一个问题（在澄清阶段）？ | 是 → 继续；否 → 删除多余问题，只保留一个 |
| 2 | 问题是否附带了 1~3 个方案选项？ | 是 → 继续；否 → 补充选项（除非是二元问题） |
| 3 | 需求清单是否已达到"完备"？ | 否 → 继续澄清（禁止输出代码）；是 → 进入终审确认 |
| 4 | 用户已确认最终方案并明确声称执行？ | 是 → 可进入编码；否 → 等待用户确认和声称 |
| 5 | 实现方案是否安排运行时动态创建新 GameObject？ | 否 → 继续；是 → 若用户已明确强烈要求运行时动态创建则继续（并在需求清单注明「运行时动态创建」），否则改为登记「需手动注册的编辑器对象」清单后继续 |
| 6 | 本轮需求推进后，对应档案是否已按约束 7 更新（且始终仅一份档案）？ | 是 → 继续；否 → 先更新档案 |
| 7 | 是否已（或即将）调用结构化提问工具（ask 工具等）？ | 否 → 继续；是 → 撤回工具调用，改为正文文本发问 |

任何一项不通过，都必须**先修正再输出**，不得绕过。

### 约束 6：新 GameObject 默认手动注册；用户强烈要求时允许运行时动态创建

- 实现方只负责**修改代码逻辑**；对于“当前项目不存在类似内容且需注册”的新 GameObject（含预制体、场景对象、UI 节点等），**默认禁止在代码运行时动态创建**（如 `new GameObject()`、运行时构建 UI 层级等）。
- 此类对象默认由**用户在 Unity 编辑器中手动创建/注册**（创建对象、挂载脚本、拖好 Inspector 序列化引用、配置到场景/Addressables 等）后，代码再通过序列化引用或配置加载/使用它。
- **例外：当用户明确强烈要求运行时动态创建新 GameObject 时，允许在代码运行时创建**（如 `new GameObject()`）。此例外以用户当前对话中的明确表态为准；此时该对象无需登记进「需手动注册的编辑器对象」清单，但需在需求清单中注明「运行时动态创建」并说明其创建/销毁生命周期。
- 凡采用手动注册的新增对象，必须在需求清单中同步维护「需手动注册的编辑器对象」清单，逐项列明：对象名称、需挂载脚本、需拖入的序列化引用、注册位置（场景/预制体/Addressables 等），并在终审确认时整体交付用户注册。

### 约束 7：档案化记录（一次调用一份档案，随推进更新）

- **一次流程调用仅产生一份档案**：本 skill 每一次被调用（含主流程与每一层递归流程），自流程启动、需求清单建立后即建立唯一一份档案；此后所有推进事件均**更新同一份档案**（整体覆写内容并追加更新时间线），禁止为同一调用另建档案或产生多份文件。
- 档案命名：`澄清-YYYYMMDD-HHMMSS_主题简称.md`，其中 `澄清-` 前缀标识本 skill 流程（与开发流程的 `开发-` 前缀区分），`YYYYMMDD-HHMMSS` 为流程启动时间戳；不同调用（含每一层递归）的名字均不相同，可直接从文件名辨别档案归属的流程。
- 归档位置：桌面「流程归档」文件夹（实际路径：`C:\Users\11\Desktop\流程归档\`；如不存在则先创建）。
- **档案写入方式（暂存-复制）**：写入类工具无法直接写入工作区外的桌面路径（会报 `can not edit the file outside the projects`），建档与更新一律按四步执行：① 将档案（同名文件）先写入当前工作区内的临时暂存位置（如 `.tmp_addr\` 文件夹）；② 用 PowerShell `Copy-Item` 将暂存文件复制到「流程归档」文件夹（字节级复制、保持编码不变，中文路径可直接使用）；③ 校验一致性：`Test-Path` 确认目标存在、`Get-FileHash` 比对源与目标哈希相等；④ 用删除文件工具删除暂存文件、不留残留。更新档案时同样先写暂存、再复制覆盖到既有档案路径。
- **更新事件点**（保持档案内容始终最新）：① 流程启动、需求清单建立后立即建档；② 每当需求推进（每次迭代问答将结果整合进需求清单后）时更新；③ 终审定稿时做终版更新；④ 流程终止（用户放弃等）时更新并标注「已终止」。
- 档案必须包含：档案名、流程类型（主流程/递归流程）、状态（进行中/已结束/已终止）、启动时间、更新时间线（每次更新追加：时间 + 推进摘要）、父档案与子档案（如发生嵌套）、方案记录、最新版需求清单、终审结果、需手动注册的编辑器对象清单。
- **档案边界（先澄清后开发）**：一次调用一份档案、互不合并——澄清流程结束后进入 `incremental-dev` 开发流程时，由开发流程**另行建立独立档案**（`开发-` 前缀），与本档案为先后接续的两份独立档案；同一功能的澄清与开发档案沿用**相同的主题简称**，凭文件名配对查阅。仅当本流程**进行中**调用其他流程（如递归澄清）时，才适用下方的「嵌套与回归」。
- **嵌套与回归**：流程进行中因调用其他流程产生新档案时——在**旧档案**中说明（记录新档案名与产生原因，并标注本档案暂缓更新）；**新档案**结束时标注「已结束」并写明回归的父档案名；随后**旧档案**追加一条「嵌套流程已结束，本档案恢复更新」，继续按推进事件更新。
- 递归澄清流程同样适用本条，不得因嵌套或暂缓而省略记录。

## 触发场景

当用户提出一个新的功能需求、特性请求或修改要求时，自动启用本 skill 进行需求澄清。

当本 skill 在外层任务（实现任务或另一澄清流程）进行中被调用时，以**递归澄清流程**方式运行：使用独立需求清单、独立档案（`澄清-` 前缀独立时间戳，嵌套与回归按约束 7 记录），终审确认后回到被挂起的外层任务（详见 `ask-via-clarify` skill 的约束 5）。

## 核心原则

1. **一次只问一个问题** — 每次提问仅聚焦一个未阐明的方面，避免多个问题同时抛出造成混乱
2. **提供选项而非开放问题** — 每次提问给出你认为可能合适的 1~3 条方案选项供用户选择
3. **迭代推进** — 每获得一次回答后，将结果整合进需求清单，基于更新后的清单提出下一个问题
4. **完备即止** — 当需求清单足够清晰、完整、可执行时，停止提问
5. **文本发问、禁用弹窗工具** — 提问一律以回复正文的文本形式呈现，禁止调用 `ask` 等结构化提问工具（与约束 1 对齐）

## 执行流程

### 步骤 1：初始化需求清单

- 解析用户的需求描述，提取已明确的信息，整理成结构化需求清单
- 需求清单应包含：功能描述、交互方式、数据流、UI 表现、边界条件等维度
- 标记出当前清单中模糊、缺失或矛盾的部分

### 步骤 2：阅读相关工程文件

- 搜索并阅读与需求相关的现有代码、配置、预制体、设计文档等
- 了解现有的架构模式、编码规范和实现约束
- 将工程上下文整合进需求理解中，避免提出与现有设计冲突的问题

### 步骤 3：迭代提问

每次迭代：

1. 审视当前需求清单，找出最关键的待澄清点
2. 针对该点提出一个问题
3. 提供 1~3 个你认为合理可行的方案选项供用户选择
4. 等待用户回答

### 步骤 4：整合与更新

- 将用户的回答及选择的方案整合进需求清单
- 更新清单中对应条目的状态为「已确认」
- 如果用户的选择引入了新的模糊点，标记为新待澄清项

### 步骤 5：终审确认

在需求清单已完备、迭代提问终止后：

- 重新审查相关的工程代码、配置文件、预制体等
- 对照需求清单逐项核查，检查是否存在：
  - 与现有架构/实现冲突的条目
  - 遗漏的边界情况或异常流程
  - 前后决策之间的矛盾
  - 缺少必要输入/输出数据的环节
- 若发现纰漏，标记为新的待澄清项，回到步骤 3 继续迭代
- 若确认不存在纰漏，则最终定稿需求清单，并**立即按约束 7 做档案终版更新**（状态标注为「已结束」，写入终审结果）

### 步骤 6：循环与终止

- 回到步骤 3，基于更新后的清单继续提问
- 终止条件（满足任一即可）：
  - 需求清单中所有关键字段均已确认
  - 剩余未确认项不影响功能实现的主流程
  - 用户明确表示清单已足够完备

## 需求清单模板

使用以下结构化格式维护需求清单：

```markdown
## 需求清单：[功能名称]

### 已确认
- [x] 条目 1（描述+确认的决策）
- [x] 条目 2

### 待澄清
- [ ] 条目 3（当前待解决的问题）
- [ ] 条目 4

### 需手动注册的编辑器对象（约束 6）
- [ ] 对象名 / 挂载脚本 / 序列化引用 / 注册位置（无新增对象时写“无”）

### 方案记录
- 条目 3 → 已提供选项 A/B/C，等待用户选择
- 条目 5 → 用户选择了方案 B
```

## 档案模板（约束 7）

每次流程调用建立一份档案并随推进更新（文件名：`澄清-YYYYMMDD-HHMMSS_主题简称.md`）：

```markdown

- 档案名：澄清-20261006-143025_电梯菜单改造.md
- 流程类型：主流程 / 递归流程
- 状态：进行中 / 已结束 / 已终止
- 启动时间：YYYY-MM-DD HH:MM
- 父档案：____（递归流程填写父档案名，主流程填“无”）
- 子档案：____（发生嵌套时填写子档案名，无则填“无”）
- 被挂起的外层任务：____（递归流程填写，无则填“无”）
- 主题：____

## 更新时间线
- 2026-10-06 14:35 流程启动，需求清单建立
- 2026-10-06 14:52 需求推进：条目 1 确认（方案 B）
- 2026-10-06 15:10 嵌套产生新档案「澄清-20261006-150500_xxx」，本档案暂缓更新
- 2026-10-06 15:40 嵌套流程已结束，本档案恢复更新
- 2026-10-06 16:02 终审定稿，移交实现（状态：已结束）

## 方案记录
- 条目 A → 已提供选项 ①②③；用户选择 ②
- 条目 B → ……

## 需求清单（最新版）
- [x] ……
- [ ] ……

## 终审结果
- 未到终审写“未到终审”；定稿后写：无纰漏 / 发现纰漏项及处置

## 需手动注册的编辑器对象（约束 6）
- 无 / 对象名 / 挂载脚本 / 序列化引用 / 注册位置
```

## 提问示例

**不好的提问方式：**
> "这个功能需要怎么触发？数据从哪里来？UI 怎么展示？有没有边界情况要处理？"

**好的提问方式：**
> **问题：这个功能的触发方式是什么？**
> A. 点击按钮手动触发
> B. 进入场景时自动触发
> C. 通过拖拽物品到目标区域触发

## 注意事项

- 优先澄清影响架构设计和高层决策的问题（如数据流向、模块边界），再处理细节问题（如 UI 布局、颜色）
- 如果某个问题可以从现有工程文件中找到明确答案，不要提问，直接补充进清单
- 每次提问尽量附带工程上下文依据，如 "当前项目中同类功能的实现方式是 X，新功能是否沿用相同模式？"
- 记录所有已确认的决策，避免后续重复提问
- 涉及新增 GameObject 时，先检查项目中是否已有类似对象可复用；确需新增的，默认登记进「需手动注册的编辑器对象」清单交由用户手动注册；仅当用户明确强烈要求运行时动态创建时，才允许在实现安排中引入运行时动态创建（此时在需求清单注明「运行时动态创建」）
