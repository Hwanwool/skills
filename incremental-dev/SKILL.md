# 增量迭代开发（Incremental Development）

## ⚠️ 强制性约束（必须遵守，违反即流程失效）

以下规则是**硬性约束**，优先级高于本文件中所有其他指导性描述。任何违反这些约束的行为都意味着本 skill 流程失效，必须立即回退纠正。

### 约束 1：一次只做一个单元

- **每轮对话只输出一个单元的代码**。禁止在同一轮回复中输出多个单元的代码。
- 若某个单元涉及多个文件/代码块，它们都属于"当前单元"，可以同时输出，但这不视为多个单元。
- 如果发现自己正在输出或计划输出后续单元的代码，必须立即停止并删除那些代码。
- 如果清单尚未创建（步骤 1-2 未完成），则本轮不能输出任何实现代码。

### 约束 2：清单驱动，代码跟随

- 每次回复必须先输出最新的任务清单，再输出当前单元的代码。清单必须放在回复的最顶部或接近顶部的位置。
- 清单中状态为 **[进行中] 的单元，才是本轮唯一可以实现的单元**。
- 若清单中所有单元均为 [待开始]，则本轮仅能进行步骤 1-2（需求分析 + 单元拆解 + 清单创建），**不能输出任何实现代码**。
- 若对话上下文中已找不到清单，必须先读取工程根目录的 `unit_design.md` 恢复（见约束 5），不得凭记忆重建。

### 约束 3：实现即停，等待用户

- 当前单元的代码全部输出完毕后，**必须主动停止**，明确告知用户测试内容和验证方法，然后等待用户反馈。
- 不得自行推进下一单元，不得在用户未确认的情况下输出下一个单元的任何代码。
- 用户确认无误的标志是用户主动回复"没问题"、"继续"、"确认"等确认性消息，或者明确要求进入下一单元。

### 约束 4：响应前自我审查

在每次**即将输出实现代码**前，必须按以下顺序做自我审查，全部通过才能输出：

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 清单已创建且已获用户确认？ | 是 → 继续；否 → 只能做步骤 1-2 |
| 2 | 当前单元是否为 [进行中] 状态？ | 是 → 继续；否 → 将目标单元标记为 [进行中] |
| 3 | 待输出的代码是否全部属于当前 [进行中] 单元？ | 是 → 继续；否 → 删除不属于当前单元的代码 |
| 4 | 上一个单元是否已标记为 [完成]？ | 是或这是第一个单元 → 继续；否 → 等待用户确认 |

任何一项不通过，都必须**先修正再输出**，不得绕过。

### 约束 5：清单持久化（unit_design.md）

- 任务清单一经创建并获用户确认，或之后发生任何状态变更（[待开始] → [进行中] → [完成] / [有误]），必须**立即将完整的最新清单整体覆写**保存到工程根目录的 `unit_design.md` 文件，内容与对话中展示的清单完全一致。
- 禁止只更新对话中的清单而不同步覆写文件；`unit_design.md` 中不得残留过期清单内容，每次均为整体覆写。
- 若因上下文被删节（长对话、会话恢复、记忆丢失等）导致无法从对话/记忆中找回当前清单，必须**先读取工程根目录的 `unit_design.md`** 恢复清单再继续流程；恢复后若发现清单状态与实际情况不符，以用户确认为准修正。

## 触发场景

当用户提出一个**较大且有多模块/多步骤特征**的功能需求，或者用户明确要求"拆分实现"、"分步开发"、"边测边做"时，启用本 skill。

如果需求尚未澄清，应优先调用 `req-clarify` 技能完成需求澄清，再进入本流程。

## 核心原则

1. **最小可运行单元** — 将功能拆解为每个都能独立编译、运行、调试的最小粒度，避免跨单元耦合
2. **一段对话只做一件事** — 每轮对话仅实现一个单元，禁止超前实现未来单元的代码
3. **测试前置，反馈驱动** — 每个单元实现后主动给用户留出测试时间，测试通过是进入下一单元的唯一条件
4. **缺陷优先** — 当前单元如有 bug，搁置后续所有单元，优先修复，直到用户确认无误
5. **清单驱动** — 以结构化任务清单跟踪全局进度，每次开工前明确"当前在哪一步、下一步是什么"

## 执行流程

### 步骤 1：需求分析与单元拆解

- 阅读用户的需求描述和相关工程文件，充分理解功能全貌
- 将整体功能拆解为若干**可独立运行和调试**的子单元，每个单元应满足：
  - 有明确的输入/输出边界
  - 可单独编译通过
  - 可在编辑器中独立验证（如：单独的测试场景、显式的 Log 输出、可点击的测试入口等）
  - 不依赖后续单元即可观察其行为正确与否
- 拆解原则：
  - 按**数据层 → 逻辑层 → 表现层**的依赖方向拆分
  - 优先实现基础数据结构与工具函数，再实现核心逻辑，最后接入 UI/表现
  - 如果无法完全解耦，使用 mock/stub/接口抽象来隔离依赖
- 与用户确认拆解方案是否合理

### 步骤 2：创建任务执行清单

将拆解结果整理为结构化清单，格式如下：

```markdown
## 执行清单：[功能名称]

| 状态 | 单元 | 描述 | 验证方式 |
|------|------|------|----------|
| [待开始] | 单元 1: xxx | 简要描述 | 如何验证 |
| [待开始] | 单元 2: xxx | 简要描述 | 如何验证 |
| [待开始] | 单元 3: xxx | 简要描述 | 如何验证 |

**图例：** [完成] 已完成并确认 | [进行中] 当前正在实现 | [待开始] 等待实现 | [有误] 存在 bug 待修复
```

- 将清单展示给用户，获得确认后进入实现阶段
- **覆写落盘**：清单一经确认，立即将完整清单整体覆写保存到工程根目录 `unit_design.md`（每次均为覆写，不保留旧内容）
- 每次状态变更时重新输出完整清单，并同步覆写 `unit_design.md`

### 步骤 3：实现当前单元

- 从清单顶部取出第一个状态为 [待开始] 的单元，标记为 [进行中]
- 仅实现该单元所需的代码和资源，**不超前编写任何后续单元的逻辑**
- 实现完成后，更新清单状态，并同步覆写 `unit_design.md`

### 步骤 4：移交测试

- 将清单当前状态展示给用户
- 明确告知用户需要测试的内容和验证方法
- **主动暂停**，等待用户进行本地测试，不要自行继续下一单元
- 给出清晰的测试指引，例如：
  > "单元 1 已完成，请打开 XX 场景验证相关功能。测试无误后告诉我，我们继续单元 2。"

### 步骤 5：处理用户反馈

用户测试后可能出现两种情况：

#### 情况 A：用户确认无误
- 将当前单元状态改为 [完成]，并同步覆写 `unit_design.md`
- 进入**步骤 6**，推进下一单元

#### 情况 B：用户报告 bug
- 将当前单元状态改为 [有误]，并同步覆写 `unit_design.md`
- **搁置所有后续单元**，专注修复当前 bug
- 修复后回到**步骤 4**，再次移交测试
- 循环直到用户确认无误（[有误] → [完成]），才允许进入下一单元

### 步骤 6：推进下一单元

- 若清单中仍有 [待开始] 单元：
  - 从 `unit_design.md` 确认当前清单状态（若对话中清单缺失则以文件为准）
  - 回到**步骤 3**，实现下一个单元
- 若清单中所有单元均为 [完成]：
  - 输出最终完成报告，汇总所有已实现的单元及关键代码位置
  - 本 skill 流程结束

### 步骤 7（可选）：全局回归测试

当所有单元完成后，建议用户进行一次完整的端到端验证，确保各单元拼接后整体功能正常。

## 任务清单模板

```markdown
## 执行清单：[功能名称]

### 当前状态总览

| # | 状态 | 单元名称 | 验证方法 |
|---|------|----------|----------|
| 1 | [完成] | 数据模型定义 | 编译通过 + 测试数据构造 |
| 2 | [进行中] | 核心逻辑实现 | 运行测试场景观察 Log |
| 3 | [待开始] | UI 交互接入 | 点击按钮观察反馈 |
| 4 | [待开始] | 保存与加载 | 重启场景后数据是否持久化 |

### 当前工作单元详情

**单元 2：核心逻辑实现**
- 已完成：XXX 方法
- 待验证：打开测试场景，检查运行结果
```

## ⚠️ 反向提示词（禁止事项）

以下行为已在实践中验证会失败，**禁止执行**；违反会导致流程中断或结果不可信：

### 中文编码兼容（终端/工具链）

1. **禁止用 Bash/PowerShell 管道读取含中文的文件**（对话历史、日志、配置、代码）——终端 GBK 编码与 UTF-8 不兼容，中文会乱码（如 `�?`、`����`），读出的内容不可信。读取文件一律使用 Read / Grep / Glob 等文件工具。
2. **禁止在 Bash 命令中编写含 `$` 变量的 PowerShell 内联脚本**——外层 shell 会先吞掉 `$变量` 导致解析失败（报错形如 "表达式或语句中包含意外的标记"），且错误信息本身是中文乱码，难以定位。需要脚本时先写入 .ps1/.cmd 文件再执行，或拆分为不含变量的简单命令。
3. **禁止依赖终端管道输出中的中文文本做验证断言**（如统计 "已入队" 行数、匹配 "[决策]" 标记）——编码转换后文本失真，计数与匹配结果不可信。改用 Grep 在目标文件中搜索，或以工具返回的结构化结果（exit code / 文件内容）为准。
4. 向控制台程序管道喂入含中文的指令时，先确认目标程序 I/O 编码（本工程 Console 已切换 UTF-8）；编码不一致时改用脚本文件逐行喂入，避免管道中文截断。

## 注意事项

- 单元粒度要适中：太小则对话轮次过多效率低，太大则失去拆分意义。一个单元的理想工作量是 10~30 分钟实现 + 5 分钟验证
- 如果实现过程中发现当前单元仍有隐藏复杂度，可以进一步拆分为子单元，更新清单
- 依赖外部资源（如 Excel 配置、预制体）的单元，优先确保资源就绪或提供 mock 替代
- 每次移交测试时确保代码已编译通过，不要交给用户一个无法运行的状态
- 清单以 `unit_design.md` 为准跨轮恢复：若新对话中清单因上下文删节丢失，先读取该文件再继续，不要凭记忆重建清单
- 用户反馈 bug 时，先理解问题范围，如果 bug 是由先前已确认 [完成] 的单元引入的，也需要一并修复
- 如果用户长时间未反馈，可以主动询问测试进度
