# 提问重定向与澄清调度（Ask via Clarify）

## ⚠️ 强制性约束（必须遵守，违反即流程失效）

以下规则是**硬性约束**，优先级高于本文件中所有其他指导性描述。任何违反这些约束的行为都意味着本 skill 流程失效，必须立即回退纠正。

### 约束 1：禁止结构化弹窗提问

- **任何情况下不得调用结构化选项弹窗类提问工具**（Qoder 的 AskUserQuestion、omp 的 ask 工具等），或任何形式的弹窗式提问。
- 所有提问一律以回复正文的**文本**形式呈现。
- 用户即使口头提到"弹窗选择"等表述，也保持文本发问方式。

### 约束 2：提问前必须先检查 req-clarify 状态

- 识别到提问意图后，**不要立即发问**；先检查本会话中 req-clarify 是否已激活（已调用过，或正在按其流程工作）：
  - **已激活** → 直接按 req-clarify 的提问模式发问（与本 skill 约束 3 对齐）。
  - **未激活** → 按「约束 4：场景分流」处置。
- 禁止跳过状态检查直接提问。

### 约束 3：提问格式统一为「单问题 + 选项」

无论处于哪种场景，提问必须满足：

- 一次只问一个问题，禁止在同一轮回复中抛出多个问题或多个待澄清点；
- 每个问题附 1~3 条方案选项供用户选择（除非该问题确实只有二元答案）；
- 尽可能附带工程上下文依据（如"当前项目中同类功能的实现方式是 X，新功能是否沿用相同模式？"）；
- 提供选项而非开放问题。

### 约束 4：场景分流（req-clarify 未激活时）

| 场景 | 处置 |
|------|------|
| 常规场景：新功能需求、需求/方案本身不明确 | **调用 req-clarify**，进入其完整澄清流程（含终审与归档） |
| 实现阶段场景：任务已确认并正在实现，仅需澄清实现细节或一般问题 | **仅借用提问模式**：按约束 3 发问；不启动完整澄清流程、不中断实现节奏；得到回答后直接继续原任务 |
| 用户明确要求场景：外层任务进行中，用户明确要求"开启 req-clarify / 走澄清流程" | **转入约束 5 的递归澄清流程** |

### 约束 5：递归澄清流程（用户明确要求时）

当外层任务（实现任务、或另一澄清流程）进行中，用户明确要求开启 req-clarify：

1. **暂缓外层任务**：立即挂起外层任务，并在回复中明确告知用户"外层任务已挂起、将在递归流程完成后恢复"；
2. **调用 req-clarify**：以**递归澄清流程**方式运行完整流程（独立需求清单 → 迭代提问 → 终审确认），不得因嵌套而精简流程；
3. **档案与嵌套**：递归流程按 req-clarify 约束 7 建立独立档案（`澄清-` 前缀 + 独立时间戳），注明「递归流程」、父档案与被挂起任务；嵌套产生时在**旧档案**中说明（记录新档案名与原因，并标注暂缓更新）；递归流程结束时在新档案标注「已结束」与回归的父档案名，随后旧档案追加「恢复更新」并继续推进；每一层流程一份档案，互不覆盖；
4. **恢复外层任务**：递归流程终审定稿、并经用户确认声称继续后，恢复被挂起的外层任务，回到中断点继续；
5. 递归可嵌套于任意进行中的流程之内（含另一澄清流程），嵌套深度不限，每层独立档案、独立归档。

### 约束 6：响应前自我审查

在每次即将输出前，按以下顺序做自我审查，全部通过才能输出：

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 本轮是否存在提问意图？ | 否 → 正常输出；是 → 进入第 2 项 |
| 2 | 是否已（或即将）调用结构化提问工具（AskUserQuestion / ask 等）？ | 否 → 继续；是 → 改为文本发问 |
| 3 | req-clarify 状态是否已检查并按场景分流？ | 是 → 继续；否 → 回到约束 2 |
| 4 | 本轮问题是否只有一个且附有 1~3 选项？ | 是 → 继续；否 → 精简修正 |
| 5 | 若触发递归流程：外层任务挂起是否已声明、档案嵌套（旧档案说明/新档案建立）是否已安排？ | 是 → 继续；否 → 补全 |

任何一项不通过，都必须**先修正再输出**，不得绕过。

## 触发场景（自动生效，无需用户显式调用）

- 准备调用结构化提问工具（AskUserQuestion / ask 等）时（一律拦截并替换为文本发问）
- 需要向用户提问、征求选择、请求确认、收集补充输入时
- 需要澄清模糊点、决策分歧或方案取舍时

## 归档引用

流程档案统一存放于桌面「流程归档」文件夹（`C:\Users\11\Desktop\流程归档\`）：

- 澄清流程（含递归）遵循 req-clarify 约束 7：一次调用一份档案（`澄清-YYYYMMDD-HHMMSS_主题.md`），随需求推进持续更新；
- 开发流程遵循 incremental-dev 约束 6：一次调用一份档案（`开发-YYYYMMDD-HHMMSS_主题.md`），随单元推进持续更新；
- 两类档案文件名前缀不同，可直接辨别所属流程，同一功能的澄清与开发档案沿用相同主题简称、凭文件名配对；澄清与开发为先后接续的**独立档案、互不合并**，仅当流程**进行中**调用其他流程时才构成嵌套（旧档案说明、新档案结束时标注回归）。
- 档案写入统一采用「暂存-复制」方式：先写工作区内暂存文件 → `Copy-Item` 至桌面归档 → `Test-Path`/`Get-FileHash` 校验 → 清理暂存（写入类工具无法直接写工作区外路径；执行细节见 req-clarify 约束 7 与 incremental-dev 约束 6）。

## 示例

**错误 1——弹窗提问：** 调用 AskUserQuestion / ask 等结构化工具弹出选项界面。

**错误 2——多问题堆砌：** "触发方式是什么？数据从哪来？UI 怎么展示？"

**错误 3——实现阶段打断节奏：** 实现中途的小问题直接启动完整澄清流程（用户未明确要求时）。

**正确 1——实现阶段仅借用提问模式：**
> **问题：该按钮应放在哪一侧？**
> A. 左侧
> B. 右侧

**正确 2——递归流程开场：**
> 收到。外层实现任务将暂缓挂起，现以递归澄清流程处理该问题（归档编号 20261006-143025）。
> **问题：……？**
> A. ……
> B. ……

## 常见误区

- ❌ "只是小问题，弹窗更快" → 一律文本单问题，无例外
- ❌ 实现阶段提问时顺手启动完整澄清流程 → 仅借用提问模式，除非用户明确要求递归
- ❌ 递归流程结束后忘记恢复外层任务、或忘记归档 → 恢复与归档是递归流程的收尾必做项
- ❌ 一轮回复提出多个问题"顺便都问了" → 只保留最核心的一个
